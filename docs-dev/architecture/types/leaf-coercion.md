# Leaf coercion

`_coerce_leaf` converts to bool, int, float, str, None, `Literal`, `Enum`, registered leaf types (`Final[T]` reaches it as `T`, [introspection](introspection.md#wrappers-are-transparent)) and `Any`.
Policies:

- bool words: true/1/yes/on, false/0/no/off (case-insensitive); None words: none/null, and the empty string for a `None` target;
- `int(text, 0)`: `0x10`, `0o7`, `0b1`, `1_000` accepted (so `08` is rejected);
- a real `bool` is never accepted as an int or float;
- a `float` reads a native `int` as its digits read, and a finite number too large for a float as the infinity of its sign, with a `FloatOverflowWarning`; an `int` never reads a native `float` ([design decisions](../design-decisions/a-float-reads-an-int-as-its-digits.md#a-float-reads-an-int-as-its-digits));
- Enum: member name first, then `str(value)`;
- a subclass of `str`, `int` or `float`: coerced as that builtin, then given to the class, which may refuse it; it ranks as the builtin, and a token is coerced eagerly to the plain builtin, which the merged dict holds as a file would ([design decisions](../design-decisions/a-builtins-subclass-is-that-builtin.md#a-subclass-is-built-by-its-constructor));
- Literal: the members a value spells, an int, str, bool, `Enum` member or `None` (`_types._literal_values`); a `bytes` member reads as nothing, and any other member PEP 586 forbids makes the annotation invalid, refused wherever a value reaches it ([design decisions](../design-decisions/a-literal-member-is-what-pep-586-allows.md#a-literal-member-is-what-pep-586-allows));
- tokens only: any other native value from a file must already have the right type.

`Any` holds every value: a leaf passes through, a token as the plain `str` it spells, CSV keys included ([tokens never leak](token-model.md#token-model)).
`_coerce._held_by_any` is that leaf pass-through, and the only one: `construct()`'s `ANY` branch asks it of every leaf it reaches, and so does `_coerce_leaf`, which a dict's key coercion asks of an `Any` key annotation directly, without the shape dispatch that handles `ANY` everywhere else (BUG-212).
A container is no leaf: `_construct._construct_any` reads a dict holding an opener as a spec and walks any other dict or list as `dict[Any, Any]` or `list[Any]` ([callables](../callables.md#an-any-node-reads-every-opener)).
A container in which nothing changed is returned as the very object given, so a caller's dict passed to `from_dict()` stays that dict.

**Registry**: `_LEAF_COERCIONS` maps a type to a coerce function and `_LEAF_SERIALIZERS` maps it to the inverse; `register_leaf_type` writes both, and `Path`, `Decimal`, `UUID` and the date and time types are simply entries of each ([Decimal and UUID](../design-decisions/decimal-and-uuid-are-built-in-leaves.md#decimal-and-uuid-are-built-in-leaves), [the date and time types](../design-decisions/the-date-and-time-types-are-built-in-leaves.md#the-date-and-time-types-are-built-in-leaves)), so built-in and user leaf types are one mechanism.
`register_leaf_type` refuses, with a `TypeError`, a key construction never asks the registry for — no class, a class a shape or a built-in leaf claims first, or `object` — so no registration is accepted and then ignored (`_registration_refusal`, [design decisions](../design-decisions/a-registration-is-one-construction-reaches.md#a-registration-is-one-construction-reaches)).
A value is an instance of one registered type, its most specific: `_registered_leaf_of` answers with the first registered class of its MRO, so a `datetime` is a `datetime`, not the `date` it subclasses.
`_coerce_registered` passes a value through only when that type is the target, and `_serialize._object_form` writes it with that type's serializer ([design decisions](../design-decisions/the-date-and-time-types-are-built-in-leaves.md#an-instance-is-its-most-specific-registered-type)).
A registered type is treated as a leaf even if it looks like a struct, in **both** directions: construction skips the struct branch for it (`_construct_typed`) and so does serialization (`_serialize_by_type`).
The one way back in is an explicit class tag: `_is_taggable_leaf` marks a struct-shaped registered type, and `_construct_scalar` hands a dict carrying the tag to `_construct_struct_dispatch` and rejects one without it ([design decisions](../design-decisions/an-explicit-tag-opts-a-leaf-back-in.md#an-explicit-tag-opts-a-leaf-back-in)).
`_is_struct_variant` is the one function that answers "does this type get taken apart into fields?" — `_is_struct` minus the registry — and both dispatchers (through `_type_kind`, which names such a type `TAGGABLE_LEAF`, see [shape dispatch](introspection.md#shape-dispatch)) and both union-variant filters (`_construct_union`'s `dc_vars` and its complement in `_construct_union_leaf`, `_serialize._needs_tag`) go through it ([invariants](../invariants.md#delegate-to-the-canonical-function)).
Asking `_is_struct` directly is the mistake: a registered leaf may have an `__init__` — `UUID` has one with a default for every parameter — so a `Release | UUID` field otherwise looks like a union of two structs and is neither ambiguous on the way in nor in need of a tag on the way out ([design decisions](../design-decisions/registered-leaf-is-never-a-struct-variant.md#a-registered-leaf-is-never-a-struct-variant)).
`_construct_union_leaf` then splits what is left three ways, each bucket decided by a canonical function rather than by a type test spelled out in place: **fixed-arity sequences** (`_fixed_seq_types(...) is not None` — `tuple[X, Y]` *and* a namedtuple), tried first and filtered on the arity that same function reports; **variable-length collections and dicts** (`_is_varlen_collection` or `_is_dict`, which is where `tuple[X, ...]` belongs, not with the fixed ones); and the **scalar leaves**, whatever is left.
Asking `_is_tuple` for the first bucket is the mistake it used to make: a namedtuple is a tuple subclass, not a `tuple[...]` generic alias, so `str | Point` landed among the scalars and refused the list `str | tuple[int, int]` accepts — in every channel, since this is below the parsers ([design decisions](../design-decisions/namedtuple-is-a-fixed-length-sequence.md#a-namedtuple-is-a-fixed-length-sequence)).

Coerce functions may raise `ValueError`, `TypeError` or `OSError`; a built-in one raises `_LeafRefusal`, a `ValueError` whose hint, the form the type reads, ends the `TypeCoercionError`; `serialize` defaults to `str` (`Path`'s is `as_posix`, so a dump is portable) and must return something a config writer accepts and `coerce` reads back ([design decisions](../design-decisions/registered-leaf-serializer.md#registered-leaf-types-dump-through-a-registered-serializer)).

`_try_coerce` (eager, used by parsers) never raises: it coerces only unambiguous targets and returns the token unchanged otherwise, leaving the decision to `construct`.
`_coerce_leaf` raises.
Pick deliberately: overrides of locals use `_coerce_leaf` because a failure must be an error there ([locals](../locals.md#declare-in-files-modify-anywhere)).
Expression tokens are skipped by rule ([expressions](../expressions/deferral-rule.md#deferral-rule)).
The two share one predicate for "is this leaf type coerced eagerly?" — `_is_eagerly_coercible`, the eager subset of `_coerce_leaf`'s domain: the types whose value a file holds natively, so `str` and every type `_reads_as_object` names are excluded — and diverge only on raise-vs-return ([invariants](../invariants.md#delegate-to-the-canonical-function)).

`read_as_object` is the third reader: what an expression reads of a leaf, the value construction builds where one `_reads_as_object` or `_is_eagerly_coercible` type is certain — the object, or a file's `1` as the `1.0` a `float` holds — the value as written anywhere else and wherever the type refuses it.
It never raises either, and never warns ([design decisions](../design-decisions/an-expression-reads-a-typed-leaf-as-its-object.md#an-expression-reads-a-typed-leaf-as-its-object)).
